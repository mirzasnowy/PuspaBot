## Chassis integration — `puspa/chassis/` (DONE 17 Nov 2026)

Mapping of nanobot hook points (confirmed from reading nanobot's code, not assumed):
- nanobot's official hook (`AgentHook`) is observation ONLY — `before_execute_tool` has no return value, no veto. So the hook is NOT used as a permission gate.
- The fast execution path (`execution.py:190`) calls `tool.execute` directly and bypasses `registry.execute` — wrapping `registry.execute` alone is not enough.
- nanobot skills have NO signature verification at all (only frontmatter `name` + `description`).
- `SubagentManager.spawn` has no token/permission slot; a subagent's `RequestContext` is built without `attributes`.

Wiring built (all via nanobot's official constructor parameters / subclasses):
- `puspa/chassis/context.py` — ContextVar for this turn's permission token (an ALREADY-verified payload dict; raw strings rejected) + fallback read of `RequestContext.attributes["puspa_token"]` + `make_ledger_sink` (ledger -> callable `log(event_type, content)`).
- `puspa/chassis/tools.py` — `PuspaTool(Tool)`: check token (no token -> fail-closed rejection) -> check the tool name in `payload["tools"]` -> if the tool has a skill manifest, `check_tool` (with signature verification, see decision 7) -> if the tool maps to an outbound action kind, go through `Gate.request_approval` (no gate -> reject; if the gate creates a request, return the "Menunggu persetujuan" error WITHOUT executing) -> execute the real tool -> scan the string result for injection (detect only, recorded in `tool_completed`; blocking is the verifier's job in phase 2) -> audit `tool_called` + `tool_completed` (without parameter contents — they can hold sensitive data).
- `puspa/chassis/registry.py` — `PuspaRegistry(ToolRegistry)`: `register` wraps every tool once (anti-double-wrap); override `prepare_call` as a backstop (a tool that slips through unwrapped still gets its token checked, rejected + recorded).
- `puspa/chassis/hooks.py` — `PuspaHook(AgentHook)` observation only: `before_run` -> `task_created`, `after_run` -> `task_completed` + `agent_message` (truncated to 2000 characters), `on_error` -> `task_failed`. The orphan-number rule (`finalize_content`) is NOT yet enforced — phase 2.
- `puspa/chassis/skill_loader.py` — `PuspaSkillsLoader(SkillsLoader)` overrides `_load_skill`: workspace/plugin skills MUST pass `verify_skill` (without `public_key` -> all rejected); nanobot builtin skills are trusted as part of the chassis.
- `puspa/chassis/agent_session.py` — `bind_turn`: validate the login session (`validate_session`) -> issue an Ed25519 agent permission token (default budget 25 steps / 100,000 tokens / Rp0, optional `task_id` in the payload).
- `puspa/chassis/sandbox_tool.py` — `SandboxTool(Tool)`: code execution via `puspa.sandbox.Sandbox`; if the sandbox is unavailable -> `ToolResult.error` (never executes on the host). nanobot's builtin shell tool is not in Puspa's token list.
- `puspa/chassis/factory.py` — `PuspaChassis` (config dataclass) + `build_registry` / `build_hook_factory` / `assemble` (assembles `AgentLoop.from_config` with Puspa's registry + hook + hook factory; `SandboxTool` is registered first so nanobot's `ToolLoader` does not overwrite it).
- Subagent token mechanism: the Puspa ContextVar set around `spawn()` is visible inside the subagent because `asyncio.create_task` copies the context (tested). Alternative NOT chosen: subclassing `SubagentManager` (internal, fragile).

NOT YET (phase 2): an end-to-end turn test with the real `AgentLoop` + model provider (needs the whole nanobot tool dependency tree + a stub provider — postponed, not skipped); closing the approval->execution async flow (synchronous Gate.execute, async tool — needs an async-aware path); blocking/rewriting toxic results by the verifier + renderer (definition 2.5); ledger policy when Postgres is down (fail-closed vs re-queue); moving `Sandbox.run` to an executor (it currently blocks the event loop briefly).

## Recorded decisions (Nero only needs to act if he disagrees)
1. **Tombstone without UPDATE.** Definition 2.3 forbids UPDATE/DELETE on the `events` table BUT also says deleted event content is replaced with a deletion mark. Decision: delete = append `task_stopped` with `content={"deleted": true}`; projections hide the task. Append-only is kept as the stronger invariant.
2. **Rp0 limit = two independent checks.** Approval AND the spending limit are checked separately at the gate; the default Rp0 limit means any payment stays blocked until the user raises the limit in Settings (the `set_limit` API exists; Settings UI in phase 2).
3. **Keys created at runtime/test time**, never stored in a file. The vault master key comes only from env `PUSPA_VAULT_MASTER_KEY`; without the env, the vault raises (no default key).
4. **Passwordless test DB**: peer auth as the OS user (`root`) via socket; default DSN `dbname=puspa_test user=root host=/var/run/postgresql`, overridable via env `PUSPA_TEST_DSN`.
5. **Ledger chain order (deviates from the literal contract, needs confirmation):** the contract says the chain is ordered by `id`, but `id` uses `gen_random_uuid()` so it is not ordered by insert time — the implementation uses insert order `(created_at, id)` and documents it in the `ledger.py` docstring. Alternative: UUIDv7. Final decision is the parent's/Nero's.
6. **Gate needs `public_key` for string tokens** (optional param beyond `Gate(log, spending)` in the contract): a string token without `public_key` is rejected, signatures must not be silently skipped. A token may also be given as an already-verified payload dict from the caller.
7. **`check_tool` gap — FIXED 17 Nov 2026 ~14:20 WIB (no longer a phase 2 follow-up).** `check_tool(skill, tool, public_key=None)` must now verify the signature: `public_key=None` -> fail-closed rejection (`SkillRejected`); dict manifests have their signature verified against the unsigned manifest; dirpath manifests are read from disk then verified; only after passing, tool membership is checked. New helper `_verify_manifest_dict`; `verify_skill` refactored to use it. 5 new tests in `test_policy.py` (rejected without public_key, unsigned manifest rejected even when the tool is listed, manifest changed after signing rejected, wrong key rejected, unsigned skill dir rejected) + 3 old call sites updated. `tests/test_policy.py` + `tests/test_attacks.py` = 50 passing.
8. **Permission enforcement in the wrapper + registry, NOT in the hook.** nanobot's hook cannot veto (no return value), so `PuspaTool` + `PuspaRegistry.prepare_call` are the only execution gates. The hook only observes (task lifecycle).
9. **Ledger writes from the integration layer are best-effort** (exceptions swallowed so a dead Postgres does not bring down the turn). The ledger policy during an outage (fail-closed vs queue-and-retry) is a phase 2 decision.
10. **Approval -> execution flow not yet closed for async.** `Gate.execute` is synchronous; async tool execution after the user approves in the PWA needs an async-aware path — phase 2. In phase 0, the wrapper returns the "Menunggu persetujuan" error without executing, and the gate guarantees exactly-once execution (tested).
11. **nanobot builtin skills are trusted as part of the chassis** (no Puspa signature); only workspace/plugin skills need signatures. If one name exists in both workspace and builtin, workspace wins (nanobot's rule) — so a workspace skill impersonating a builtin must still pass verification.
12. **End-to-end turn test with the real `AgentLoop` POSTPONED to phase 2** (not skipped): building the real loop pulls in the whole nanobot tool dependency tree + a stub provider. Phase 0 tests the real runner execution path (`execute_tool_calls`) + real components, and `assemble` is tested with a stubbed `AgentLoop.from_config`.
13. **Full nanobot dependencies in the venv.** The initial editable install was only partial; on 17 Nov 2026 ~14:28 WIB `pip install -e ./nanobot` was run (all of nanobot's declared dependencies: httpx, tzlocal, typer, anthropic, websockets, aiohttp, sigstore, mcp, etc.). `requirements.txt` updated with the nanobot dependencies the chassis uses + a note that nanobot is imported from the local clone, not pip.
14. **Postgres lost on VM restart (17 Nov 2026, before the integration run).** Cluster 16/main still existed but role `root`, DB `puspa_test`, and role `puspa_app` were gone. Recovered: `pg_ctlcluster 16 main start` + `CREATE ROLE root LOGIN SUPERUSER` + `CREATE DATABASE puspa_test OWNER root` + `CREATE ROLE puspa_app NOLOGIN`. If lost again after a restart, repeat these steps (the Environment section of STATUS already records the same pattern for the apt install).
15. **RLS without FORCE, enforced on the `puspa_app` role.** RLS is enabled on the users/sessions/vault tables WITHOUT `FORCE ROW LEVEL SECURITY`: the table owner/superuser still bypasses RLS (a Postgres property, not a bug — tested in `test_rls.py`). Real enforcement only applies to connections as the `puspa_app` role (NOLOGIN; connections run as the owner then `SET ROLE puspa_app`). Exception: registration INSERT without a session is allowed — the users INSERT policy allows an empty `app.current_user_id` (chicken-and-egg: before the session is validated, the user_id is not known yet). Login/registration/session-validation operations run as the table owner; only after the user_id is known do all further queries go through `rls.as_user` as `puspa_app`.
16. **Vault derivation FROZEN.** Explicit `derive_user_key` in `puspa/accounts/vault.py`: HKDF-SHA256, length 32, salt=None, info=`str(user_id)`. These parameters must NOT change — changing them makes all existing vault ciphertext undecryptable. The master key still comes only from env `PUSPA_VAULT_MASTER_KEY`, never stored in the database.
17. **Access module + agent registry.** `puspa/accounts/access.py` is the ONLY place ownership is checked: every read API MUST call `require_owner` BEFORE touching data (before querying content, before decrypting). Ownership rejections are always `AccessDeniedError`; data that really does not exist is always `KeyError` — so another person's data existence does not leak through different error messages. A ledger event's owner is derived from the agent registry (`agent_id` -> `user_id` via the `agents` table, `puspa/accounts/schema_agent.sql`); an unregistered agent -> owner unknown -> fail-closed rejection.
18. **Session resolution without side effects (integrator's choice, 17 Nov 2026).** `resolve_session_as` uses the new owner-only lookup `user_sessions.owner_of_token` (SELECT only, no UPDATE) — NOT `validate_session` — so a token B used by A and rejected does not change session B's `last_seen_at`. `validate_session` is unchanged (legitimate session use still updates `last_seen_at`); tested by 1 new test in `test_access.py`.
19. **Ledger chain stays (created_at, id); 31 event types.** Chain order stays insert order `(created_at, id)` as in decision 5 (not `id` alone); the closed revision 7 type set = 31 types (22 old + 9 new workflow/trigger/module/report/consent), with an idempotent CHECK migration in `schema.sql` so old tables created when the set was still 22 types get updated too.
20. **Argon2id password login replaced by Google login in phase 1.** `users.py` (email + Argon2id password) stays in phase 0 as the account foundation, but phase 1 login uses Google (revision 7 decision); per-device sessions (`user_sessions.py`) + vault (`vault.py`) are reused unchanged. There is NO Google login implementation in phase 0.
21. **nanobot as a pinned git dependency; tree ready to push.** `requirements.txt` uses `nanobot-ai @ git+https://github.com/HKUDS/nanobot@e767174` (PyPI package name `nanobot-ai`, import stays `nanobot`); `tests/conftest.py` only inserts the local `./nanobot` clone into `sys.path` if the directory actually exists (a `Path.exists()` guard), so from a fresh clone tests use nanobot installed from the dependency. New `.gitignore`: `.venv/`, `__pycache__/`, `*.pyc`, `.pytest_cache/`, `nanobot/`, `*.egg-info/`. The local `nanobot/` clone stays reading reference only; the mirzasnowy/nanobot fork stays ignored, DO NOT delete it without Nero's order.
22. **`get_definitions` token-filtered (visibility layer, 17 Nov 2026 ~22:40 WIB).** `PuspaRegistry.get_definitions` now only returns the schemas of tools whose names are in this turn's token `tools` list; with no bound token, the list is empty (fail-closed). Before, the model saw ALL of nanobot's builtin tools (proven by live run 1 of the CLI: the model picked the `message` tool outside the token). This seam is safe because nanobot calls `get_definitions` per model round / during consolidation inside the turn (not once at construction), and the parent cache only stores the unfiltered full list — the filter is read from the currently active token on every call. `prepare_call` REMAINS the execution enforcer (defense in depth). The local unregister patch in the CLI (`build/cli/puspa_cli/agent.py`) is now redundant but harmless. Tested by 4 new regression tests in `tests/test_integration.py` (11 registry/chassis tests green; the full suite was NOT run because the phase 1-4 coordinators were active — the narrow tests use a throwaway DB `puspa_test_registry_fix`, not `puspa_test`). Remaining small gap (not part of this fix): the `prepare_call` error message for an unknown tool still lists the full `tool_names` — the model can read tool names from that error message; to be closed in phase 2 if needed.
