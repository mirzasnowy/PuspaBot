# i18n — server sentences in the user's language (internationalisation)

PuspaBot is Indonesia-first. Full i18n (many locales) is global-expansion
work and is **deferred** — this module is the boilerplate that makes
that expansion possible later without rewriting every user-facing
sentence. What ships now: Indonesian server-lines from the start.

## The server-lines rule

The server writes its sentences in the user's language, from a
message-key registry — never by concatenating fragments, and never by
mixing English into the Indonesian UI.

- Every sentence the user reads lives in one catalog:
  `puspa/i18n/locales/id.json`, keyed by message key
  (`error.not_logged_in`, `hint.first_approval.title`, ...).
- Code calls `puspa.i18n.server_lines.render(key, **variables)` with
  **named placeholders only** (`{nominal}`, `{ceiling}`). A sentence
  is one whole string in the catalog; call sites never assemble
  sentences from parts, so a translator later translates whole
  sentences, not fragments.
- The rule is fail-closed (`puspa/i18n/server_lines.py`):
  - Unknown key raises `UnknownMessageKey` — the server never serves
    a silently wrong sentence.
  - Missing template variable raises `MissingVariable`.
  - Unknown locale falls back to Indonesian (the default) and the
    fallback is recorded (`fallback_records()`). It never crashes,
    and it never silently serves English to an Indonesian user —
    there is no English catalog at all, so there is nothing English
    to fall back *to*.
- The default catalog loads at import time, so a broken `id.json`
  fails startup loudly instead of failing the first user who hits
  an error path.

## Locale model

- One JSON file per language in `puspa/i18n/locales/`:
  `<language>.json`, a flat object of key -> template string.
  Today only `id.json` (Indonesian, 36 keys) ships.
- Validation (`puspa/i18n/locales.py`, DuskBot pattern kept simple):
  every key in the default locale must exist in every other locale
  file, and no locale may carry a key the default does not have.
  With only `id` present the check passes trivially and guards
  future additions — a key added to `id.json` without a translation
  fails loudly instead of silently serving the wrong language.
  There is no source-hash check (DuskBot's 8 MB
  `source-hashes.json`); the key-coverage check is the honest
  minimum for one locale.
- `render(key, locale="id", **vars)`: `locale` is a language code
  like `"id"`. The PWA today always renders `"id"` — the locale is
  not yet read from the user profile or request headers (see
  Limits).

## What is wired (internationalisation)

- **PWA API errors** (`puspa/pwa/app.py`, `insights_api.py`,
  `onboarding_api.py`): the 401 `{"error": "belum masuk"}` on every
  route (17 sites), the 503 Google-login-not-configured error, and
  the 404 `{"error": "permintaan tidak dikenal"}` on
  `POST /api/persetujuan/{request_id}`. Wire responses are
  byte-identical to before — only the source of the string moved.
- **Onboarding hints** (`puspa/onboarding/hints.py`): all five
  hints (first modules visit, first approval, first memory use,
  first costly task, first billing row) now render Indonesian
  title / body / action label from server-lines. This is the one
  place the server used to write English sentences to the user.
  The costly-task body takes the ceiling as a named variable
  (`{ceiling}`, rendered as `Rp2.000` from
  `TASK_COST_CEILING_IDR`), not a hardcoded number.
- **Approval gate denials** (`puspa/policy/gate.py`): every
  Indonesian `GateDenied` message — token checks, unknown request,
  wrong owner, already-decided status, spending limit — now comes
  from server-lines, byte-identical to before. One real fix along
  the way: the old string said "tidak ada penegak batas belanja
  **belanja**" (the word repeated); the catalog carries the
  corrected sentence.

## What is deliberately NOT wired (the boundary)

- **Internal logs and English developer messages.** Log lines,
  exception messages in `puspa/accounts/`, `puspa/auth/`,
  `puspa/billing/` and other modules, and the `str(exc)` 400
  responses in the PWA API (which surface those module errors)
  stay as they are: they are written for the developer reading a
  log, not for the user reading a screen. Translating them would
  make debugging harder without improving any screen.
- **Approval decision reasons** (`puspa/policy/approvals.py`):
  `decide()` reasons stay English developer text ("rule for
  {kind}: ask every time", ...). They are asserted verbatim by
  `tests/test_approvals_taxonomy.py` and are the audit trail for
  *why* the policy asked — the user-facing side of an approval is
  the approval card (already Indonesian in the client) and the
  gate denials above, not this reason string.
- **The "content changed after approval" denial** in `gate.py`
  stays in English: it is asserted verbatim by
  `tests/test_approvals_taxonomy.py` and describes an internal
  invariant (content-hash mismatch), not a user action.
- **The trial error query param** (`/trial?error=trial_already_used`
  / `trial_unavailable` in `app.py`): an error *code* echoed into
  the template, not a sentence; the template renders the code.
- **The PWA client (TypeScript) and Jinja templates.** internationalisation wires
  the server's sentences only. Client-side copy (screens, buttons,
  the approval card) is a separate pass; the client already renders
  Indonesian labels on the approval card.

## How to add a language later (deferred)

1. Copy `locales/id.json` to `locales/<code>.json` and translate
   every value (whole sentences, placeholders untouched — a
   placeholder name must stay identical, e.g. `{nominal}`).
2. Run the locale validation: `validate_locales(load_locales(...))`
   must return no problems — every `id` key present, no orphans.
3. Add a test that renders every key in the new locale (same shape
   as `tests/test_i18n_server_lines.py::test_every_key_renders`)
   so a missing placeholder is caught before it reaches a user.
4. Only then teach the request path which locale to ask for
   (user profile / `Accept-Language`); until that step exists, a
   second catalog file is dead weight — do not add one early.
5. Never add an `en` catalog as a "fallback": the fallback is
   Indonesian by design, and an English catalog would let a bug
   silently serve English to Indonesian users.

## Limits (honest)

- One locale only. Nothing in the request path selects a locale
  yet; `render()` defaults to `"id"` and every call site today
  relies on that default.
- No pluralisation, gender, or date/number formatting rules —
  the catalog has no message that needs them yet. When one does,
  add it as a named-variable template (e.g. `{count}` +
  `{count_word}`), not as string surgery at the call site.
- No source-hash check: the key-coverage validation catches a
  missing translation, but it cannot catch a stale one (an `id`
  sentence edited without updating the other locale). That check
  earns its keep only when a second locale exists.
- The 400 responses that echo `str(exc)` still surface module
  error text verbatim; those modules are outside this pass.
