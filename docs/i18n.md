# i18n — user-facing strings in the user's language (internationalisation)

PuspaBot is Indonesia-first and grows globally: the PWA and the
console speak Indonesian by default and English when the user
asks. Two locales ship today — Indonesian (`id`, the default)
and English (`en`) — behind one language switch.

## The catalog: one file per language

- Every sentence the user reads lives in one catalog per
  language: `puspa/i18n/locales/id.json` and
  `puspa/i18n/locales/en.json`, each a flat object of message
  key -> template string (62 keys each). The two files must
  agree on keys: `validate_locales(load_locales(...))` fails
  loudly when a key is missing from one locale or orphaned in
  the other.
- Code calls `puspa.i18n.server_lines.render(key, locale,
  **variables)` with **named placeholders only** (`{nominal}`,
  `{ceiling}`, `{bot}`). A sentence is one whole string in the
  catalog; call sites never assemble sentences from parts, so a
  translator translates whole sentences, not fragments.
- Keys are namespaced by where the string is read: `error.*`
  (server errors and gate denials), `hint.*` (onboarding
  hints), `ui.*` (PWA screens: `ui.nav.*` labels,
  `ui.settings.language.*`, `ui.chat.input_placeholder`,
  `ui.login.title`), `cli.*` (console lines).

## The server-lines rule

The server writes its sentences in the user's language, from
the message-key registry — never by concatenating fragments, and
never by mixing English into the Indonesian UI.

- The rule is fail-closed (`puspa/i18n/server_lines.py`):
  - Unknown key raises `UnknownMessageKey` — the server never
    serves a silently wrong sentence.
  - Missing template variable raises `MissingVariable`.
  - A key the requested locale is missing falls back to the
    Indonesian template for that one key, and the fallback is
    recorded (`fallback_records()`). A half-translated catalog
    never renders a blank.
  - Unknown locale falls back to Indonesian (the default) and
    the fallback is recorded. It never crashes, and it never
    silently serves English to an Indonesian user who never
    picked English.
- `catalog(locale)` returns the merged catalog for a locale:
  the requested locale's strings win, missing keys are filled
  from Indonesian, so the result always has every key and never
  a blank. The PWA client reads through this (`GET
  /api/i18n/catalog`).
- The default catalog loads at import time, so a broken
  `id.json` fails startup loudly instead of failing the first
  user who hits an error path.

## The language switch (per user)

- The choice is stored per user in Postgres (table
  `user_language`, one row per user: the locale code only —
  migration `0040_user_language`; see
  `puspa/pwa/language.py`). Indonesian when nothing is stored.
- API (`puspa/pwa/language_api.py`, contract
  `docs/openapi-language.yaml`):
  - `GET /api/language` (login required) ->
    `{"locale", "available_locales"}`.
  - `POST /api/language` (login required, JSON `{"locale"}`)
    -> the saved state. An unknown locale is refused with 400.
  - `GET /api/i18n/catalog` (no login needed: UI strings carry
    no user data) -> `{"locale", "strings"}`. `?locale=en`
    previews one locale; without it, a logged-in user gets
    their stored language and an anonymous user gets
    Indonesian. An unknown `?locale=` falls back to Indonesian
    (never an error: this endpoint must never fail a page load).
- The switch itself lives on the Settings screen (SPA and the
  Jinja lite template): a select with Bahasa Indonesia /
  English. Saving it reloads the catalog, so the translated
  screens flip without a page reload.
- Server-rendered strings follow the stored language: the
  onboarding hints (`GET /api/onboarding/hints`) and the
  approval 404 (`POST /api/persetujuan/{request_id}`) answer in
  the user's language. The anonymous 401 (`belum masuk`) has no
  user to ask, so it stays Indonesian.

## The PWA client

- The client loads the catalog once at boot (`loadCatalog()` in
  `apps/pwa/src/main.tsx`, `GET /api/i18n/catalog`) and looks
  strings up with `t(key, fallback)` from
  `apps/pwa/src/state/language.ts`. The fallback is the
  hardcoded Indonesian string the screen rendered before the
  switch existed; when even that is missing, the key itself is
  rendered — never a blank. A failed catalog load keeps the
  Indonesian defaults.
- Translated today (the core screens): the nav labels
  (`ui.nav.*`, every screen), the Settings language card, the
  Chat composer placeholder (`ui.chat.input_placeholder`, with
  the `{bot}` name filled in), the Hub title, and the Login
  title. The rest of the screens still render their hardcoded
  Indonesian copy until their own pass — that is the honest
  limit, not a bug: each screen's strings move to the catalog
  when that screen is touched, never in one giant rewrite.

## The console (CLI)

- The same catalog and `render()` cover console strings:
  `puspa --lang en` (or `--lang=en`) before the subcommand, or
  the `PUSPA_LOCALE` environment variable; anything unknown
  falls back to Indonesian instead of failing. Today the
  unknown-command line (`cli.unknown_command`) is the one
  console string wired through it; the rest of the CLI help and
  output is still English developer text until its own pass.
  The flag must come before the subcommand
  (`puspa --lang en web`, not `puspa web --lang en`).

## What is wired (internationalisation)

- **PWA API errors** (`puspa/pwa/app.py`, `insights_api.py`,
  `onboarding_api.py`): the 401 `{"error": "belum masuk"}` on
  every route (17 sites), the 503 Google-login-not-configured
  error, and the 404 on `POST /api/persetujuan/{request_id}` —
  the last one now answers in the user's stored language.
- **Onboarding hints** (`puspa/onboarding/hints.py`): all five
  hints (first modules visit, first approval, first memory use,
  first costly task, first billing row) render title / body /
  action label from server-lines, in the user's language. The
  costly-task body takes the ceiling as a named variable
  (`{ceiling}`, rendered as `Rp2.000` from
  `TASK_COST_CEILING_IDR`), not a hardcoded number.
- **Approval gate denials** (`puspa/policy/gate.py`): every
  Indonesian `GateDenied` message — token checks, unknown
  request, wrong owner, already-decided status, spending limit
  — now comes from server-lines, byte-identical to before. One
  real fix along the way: the old string said "tidak ada penegak
  batas belanja **belanja**" (the word repeated); the catalog
  carries the corrected sentence.
- **PWA client** (see above): nav, Settings language card,
  Chat placeholder, Hub and Login titles.
- **CLI**: the unknown-command line in the user's language.

## What is deliberately NOT wired (the boundary)

- **Internal logs and English developer messages.** Log lines,
  exception messages in `puspa/accounts/`, `puspa/auth/`,
  `puspa/billing/` and other modules, and the `str(exc)` 400
  responses in the PWA API (which surface those module errors)
  stay as they are: they are written for the developer reading a
  log, not for the user reading a screen. Translating them would
  make debugging harder without improving any screen.
- **Approval decision reasons** (`puspa/policy/approvals.py`):
  `decide()` reasons stay English developer text ("rule for
  {kind}: ask every time", ...). They are asserted verbatim by
  `tests/test_approvals_taxonomy.py` and are the audit trail for
  *why* the policy asked — the user-facing side of an approval is
  the approval card (already Indonesian in the client) and the
  gate denials above, not this reason string.
- **The "content changed after approval" denial** in `gate.py`
  stays in English: it is asserted verbatim by
  `tests/test_approvals_taxonomy.py` and describes an internal
  invariant (content-hash mismatch), not a user action.
- **The trial error query param** (`/trial?error=trial_already_used`
  / `trial_unavailable` in `app.py`): an error *code* echoed into
  the template, not a sentence; the template renders the code.
- **The rest of the PWA screens and the CLI help.** Only the
  core screens listed above read from the catalog; the other
  screens' hardcoded Indonesian copy and the CLI's English help
  text move over screen by screen, not in one pass.
- **The Jinja lite templates.** The lite-mode pages are
  server-rendered Indonesian (the Settings lite template does
  carry the language switch, so the choice itself can be saved
  from lite mode — but the lite pages do not re-render in
  English).

## How to add a language

1. Copy `locales/id.json` to `locales/<code>.json` and translate
   every value (whole sentences, placeholders untouched — a
   placeholder name must stay identical, e.g. `{nominal}`).
2. Run the locale validation: `validate_locales(load_locales(...))`
   must return no problems — every `id` key present, no orphans.
3. Add a test that renders every key in the new locale (same
   shape as `tests/test_i18n_server_lines.py::test_every_key_renders_with_example_variables`)
   so a missing placeholder is caught before it reaches a user.
4. Offer it in the switch: add the code to
   `SUPPORTED_LOCALES` in `puspa/pwa/language.py`, to
   `LANGUAGE_OPTIONS` in `apps/pwa/src/state/language.ts`, and
   to the `--lang` choices in `puspa/cli.py`.
5. Only then is the language real: until step 4 exists, a second
   catalog file is dead weight — do not add one early.
6. Never use English as a silent fallback: the fallback is
   Indonesian by design, and an English catalog must only ever
   be served to a user who picked English (or a `?locale=en`
   preview). A missing key falls back to Indonesian, never to
   English.

## Limits (honest)

- Two locales only (Indonesian, English). Nothing in the
  request path reads `Accept-Language` yet; the locale comes
  from the stored per-user choice (PWA) or `--lang` /
  `PUSPA_LOCALE` (CLI).
- No pluralisation, gender, or date/number formatting rules —
  the catalog has no message that needs them yet. When one does,
  add it as a named-variable template (e.g. `{count}` +
  `{count_word}`), not as string surgery at the call site.
- No source-hash check: the key-coverage validation catches a
  missing translation, but it cannot catch a stale one (an `id`
  sentence edited without updating the other locale). That check
  earns its keep only when a third locale exists.
- The 400 responses that echo `str(exc)` still surface module
  error text verbatim; those modules are outside this pass.
- The lite-mode Jinja pages stay Indonesian; only the SPA
  screens listed above translate.
