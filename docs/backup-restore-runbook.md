# Backup and Restore Runbook (E-09, plan section 5.4)

Gate 15 requires a restore to a clean host within **30 minutes**.
This runbook is the operator procedure for that. It covers the
production setup (VPS), the monthly drill, and the recovery steps.

## 1. Architecture

Three parts, all needed for a real restore:

| Part | Tool | Where it lives |
| --- | --- | --- |
| Base backup + WAL archive | pgBackRest (production) | Encrypted S3-compatible object storage **outside** the VPS |
| Postgres dump (fallback) | `puspa.backup.create_backup` | Encrypted `.dump.enc` + JSON manifest, 14-day retention |
| Session database | `puspa.backup.snapshot_state_db` | Consistent SQLite copy of `state.db` per profile |
| Vault master key | `puspa.backup.escrow_vault_key` | **Separate** escrow file, mode 0600, never inside the data backup directory |

Losing the vault master key means losing **every user credential**,
even with a perfect database restore: the `vault` table holds only
ciphertext, and the key itself is never stored in the database. The
escrow is the only copy. Guard it like the data itself.

WAL archiving is what makes the 30-minute target reachable: a base
backup alone only restores data up to the backup time, while base
backup + archived WAL replays to the latest committed transaction.

## 2. Production setup (VPS)

### 2.1 pgBackRest stanza

1. Copy `infra/pgbackrest.conf.example` to `/etc/pgbackrest/pgbackrest.conf`
   (mode 0600, owner `postgres`) and fill in the real bucket, endpoint,
   and region. The file is generated by
   `puspa.backup.wal.pgbackrest_config`; keep the structure, edit values.
2. Set the repo cipher passphrase (never in the file, never in git):
   `pgbackrest --stanza=puspa stanza-create` prompts for it.
3. Put the S3 credentials in the host secret store; pgBackRest reads
   them from its config environment, not from the repo.
4. In `postgresql.conf`:
   `archive_mode = on`, `wal_level = replica`,
   `archive_command = 'pgbackrest --stanza=puspa archive-push %p'`.
   Restart Postgres (archive_mode needs a restart, not a reload).
5. Verify: `pgbackrest --stanza=puspa check` and
   `SELECT * FROM pg_stat_archiver` — `failed_count` must be 0.
   `puspa.backup.check_archiving(dsn)` reports the same in code.

Alternative backend: wal-g, driven by the environment from
`puspa.backup.walg_env` (prefix, endpoint, region; secrets from the
host secret store, never rendered). The archive command is then
`wal-g wal-push %p`.

### 2.2 Schedules

- Full base backup: weekly (`pgbackrest --stanza=puspa backup --type=full`).
- Differential: daily. WAL archiving runs continuously.
- Encrypted `pg_dump` fallback: nightly via `puspa.backup.create_backup`
  (14-day retention, pruned automatically).
- `state.db` snapshot: nightly via `puspa.backup.snapshot_state_db`.
- Vault key escrow: on every master-key rotation, via
  `puspa.backup.escrow_vault_key` — and verified with
  `puspa.backup.verify_escrowed_key` (it decrypts real vault rows).

### 2.3 Health checks

- `puspa.backup.check_archiving(dsn)`: `healthy` is False when
  archiving is off or any segment failed. Alert on any failure.
- `puspa.backup.verify_wal_chain(archive_dir)`: reports gaps in the
  archived segment sequence. A gap means point-in-time recovery
  cannot replay past it — treat as an incident, not a warning.

## 3. Monthly restore drill (with a stopwatch)

Run on the validation VPS once it exists (E-02), against a clean
host, and record the result in `docs/backup-restore-drills.md`:

```bash
python -m puspa.backup.drill --keep --work-root /tmp/drill-YYYY-MM-DD \
    --report /tmp/drill-YYYY-MM-DD.json
```

Until the VPS exists, the same command runs the local drill against a
scratch instance on this host: it proves the restore path (base
backup + WAL replay + vault key escrow + state.db snapshot) but it is
**not** a clean-host drill. Say so in the log entry.

The drill passes only when every check is green and the total stays
within 30 minutes. The post-backup canary is the key check: a vault
entry written *after* the base backup must survive, which only WAL
replay can provide.

## 4. Recovery procedure (real incident)

1. Stop the application (no new writes).
2. Provision a clean host with the same Postgres major version (16).
3. Restore the latest base backup:
   `pgbackrest --stanza=puspa --delta restore` (or copy the base
   backup directory for the local path), then set
   `restore_command` to fetch WAL from the archive.
4. Start Postgres; it replays WAL to the latest point. Wait until
   `SELECT pg_is_in_recovery()` is false.
5. Verify before opening traffic:
   - `puspa.backup.verify_escrowed_key(escrow_path, dsn)` — the
     escrowed key unlocks the vault rows.
   - Ledger hash chains verify (`Ledger(dsn).verify_chain(task_id)`).
   - Row counts match the pre-incident snapshot.
   - `state.db` snapshot restores and its SHA-256 matches the manifest.
6. If the vault key is lost, stop: the database restore is useless
   for credentials. Re-issue every user credential instead of
   pretending the restore worked.
7. Record the incident restore in `docs/backup-restore-drills.md`
   with the stopwatch times.

## 5. What is NOT backed up

- Blobs (screenshots): 30-day TTL, not part of the backup.
- The object-storage credentials and the pgBackRest cipher
  passphrase: they live in the host secret store, not in any backup.
- The live `state.db` file itself: only the snapshot is backed up;
  never copy the live file (it can be mid-write).
